买了一台线路不错的 VPS，还需要再买一台家宽落地吗？看到别人用国内入口、香港中转、台湾出口，是否也应该照着搭？

先看自己缺什么：是到服务器的连接不稳定，是目标服务需要特定地区出口，还是家里的设备没有可用的入站地址。三种问题对应三种改法，不能用“再加一跳”统一解决。

这篇从结构和适用条件讲选型，不把论坛里的个别测速当成所有用户的效果。测评指标和计费另见[测评与成本判断](/vps/reading-vps-reviews/)，Mihomo 的版本细节见[链式与回退陷阱](/vps/mihomo-chain-and-fallback/)。

## 把入口、传输和出口分开

一条代理路径可以拆成：

```text
用户 → 入口 → 中间传输 → 最终出口 → 目标服务
```

入口解决用户如何稳定接入；中间传输决定服务器之间如何互联；出口决定目标服务看到哪个 IP。

圈里的“线路机”“落地机”主要是用途描述：前者强调到用户网络的路由，后者强调出口地区、国际互联或目标网站的可用性。同一台机器可以兼任，没有规定必须买两台。

如果一台服务器已经满足实际用途，单节点通常更容易维护。增加落地应换来明确收益，例如需要另一个地区的出口，而不是为了凑齐某种流行拓扑。

## 有可用入口时，比较链式和端口转发

### 客户端链式代理

```text
客户端 → 前置代理 → 落地代理 → 网站
```

客户端同时知道前置与落地配置，按规则决定经过哪条链。适合希望在客户端管理不同用途、地区或出口的人，但每一层协议都必须兼容。

例如 Mihomo 的 `dialer-proxy` 可让一个具体出站借助另一个出站或策略组建立连接。它不等于所有 DNS 查询、规则下载和订阅更新都会自动使用这条链。[官方链式说明](https://wiki.metacubex.one/config/proxies/dialer-proxy/)

### 服务端端口转发

```text
客户端 → 前置的转发端口 → 落地服务 → 网站
```

客户端连接前置地址，后面的映射由服务器维护。它适合把入口集中在服务器端管理；多个落地也可以通过不同端口或转发规则接入。

要注意，nftables 的地址转换与 Realm、GOST 等用户态转发机制不同。用户态 TCP 转发通常接受一条连接，再建立另一条连接。“不解密业务内容”不代表没有处理 TCP，也不能把所有转发工具当成同一种实现。[Realm 项目说明](https://github.com/zhboner/realm)

链式和转发没有固定的优劣顺序。选择时问三个问题：规则放在哪里、需要哪些协议、以后由谁维护。

## NAT 和动态家宽，更适合从接入方式考虑

NAT 产品常用共享公网地址和分配端口提供入站能力，但入口 IP 与实际出站 IP 可能不同。选购时应分别确认：

- 入站用哪个地址和端口，TCP、UDP 是否都支持；
- 对外访问时用哪个地址，是否共享、是否动态变化；
- 是否有 IPv6，以及系统权限能否支持所需隧道。

独立公网 IP 也不代表全部端口开放或带宽独享。端口许可、安全组和系统防火墙仍要分别看。

### 有稳定映射端口，不必强行反向接入

如果家宽服务有可用入口，前置可以直接连接它。动态地址可通过 DDNS 更新，但 DNS 缓存、程序重新解析和重连会影响恢复时间。DDNS 不保存已有会话。

### 没有可用入站时，让家宽主动连接固定入口

```text
建立隧道：
家宽／NAT 设备 → 固定公网服务器

业务路径：
用户 → 固定入口 → 隧道 → 家宽服务 → 网站
```

少量服务端口可以比较反向服务转发；需要虚拟网段及多种 IP 业务，再考虑三层隧道。两者承担的维护工作不同，不能只按“哪个更高级”选择。

WireGuard 收到经过认证的数据包后，会学习对端最新地址；让动态设备主动连接固定服务器，可以减少服务器追踪动态地址的需要。NAT 保活用于维持映射，不能修复断网、UDP 阻断或错误路由。官方给出的常见参考是 25 秒，不是所有设备都要开启。[协议原理](https://www.wireguard.com/)、[保活说明](https://www.wireguard.com/quickstart/)

隧道恢复与应用会话恢复是两件事。最终出口 IP 改变，原有网页、下载或其他连接仍可能中断。

## IPv6 可以补路径，但要分清入口和出口

“只有 IPv6”不等于机器没用，需要分开解决：

1. 用户如何访问这台机器；
2. 这台机器如何访问仅支持 IPv4 的目标。

Cloudflare Tunnel 由源站主动建立对外连接，可以为没有公网可路由地址的资源提供接入，但它不是任意 TCP、UDP 业务的无条件 CDN 转发。[Tunnel 官方说明](https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/)

WARP 代理模式则是供指定程序使用的出站路径，不等于获得一枚可直接入站的独立 IPv4。使用任何出口工具，都要区分程序级代理与整机路由接管。

同一商家的 IPv4、IPv6 路由也可能不同。某一方向 IPv4 不理想时，IPv6 值得作为独立路径比较，但不能仅凭“支持 IPv6”推导出更快。

## Po0 和 IX 是另一类交付选择

Po0 是 PortChannel Zero 的商家及产品体系，不是通用协议。社区讨论中的一种结构是：

```text
用户 → 国内 BGP 入口
     → 支持内网互通的境外机器
     → 网站或另一台落地
```

这种结构把国内接入与境外出口分开。Po0、HaloCloud 双端交付等实例值得学习，但是否需要前置、交付几个实例、哪些产品能互通，都由具体产品决定。同属腾讯云体系或上游相同，不等于自动获得内网互通或同等级 SLA。

圈内售卖的“IX 产品”也不能直接等同于 HKIX。HKIX 是网络间互联的二层互联网交换平台，不是一张保证跨境速度的标签。[HKIX 官方定义](https://www.hkix.net/hkix/whatishkix.htm)

截至本文整理时，Po0 国内 BGP 公开页面列有实名、强制绑定鸡险、不退款、禁止回国访问，以及端口和 HTTP／HTTPS 用途限制。社区配置教程不构成用途许可，下单应以具体商品与条款为准。[官方产品规则](https://console.po0.io/store/tencent-can-bgp)

## 先确认路径，再谈优化

Tailscale 中设备互相在线，不代表已经直连。它区分 `direct`、DERP `relay` 和 `peer-relay`；网络变化时连接类型也可能变化。比较带宽前先确认实际路径，避免把中继效果误当成两机互联效果。[连接类型说明](https://tailscale.com/docs/reference/connection-types)

同样，WireGuard 配置里的 `AllowedIPs` 不等于系统路由本身。Linux `wg-quick` 默认会据此添加路由，包含 `/0` 时还会处理默认路由。不能照抄全隧道配置，再声称不影响 SSH 和其他服务。[官方手册](https://git.zx2c4.com/wireguard-tools/about/src/man/wg-quick.8)

遇到卡顿，先找出是哪一段、哪个方向、什么时间发生。没有瓶颈证据时，不先堆协议、改 BBR、套固定 MTU 或增加连接池。

## 选型时保留这条顺序

先明确用途，再确认可达性，接着比较完整路径，最后计算总成本和维护负担。

“线路好”“IP 好”“口子大”分别回答不同问题，不能互相替代。现有入口是否应该长期保留，也应通过同条件比较判断，而不是因为已经买过就认定它最优。
