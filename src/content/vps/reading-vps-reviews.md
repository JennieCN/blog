一张千兆测速图，不能回答你家晚高峰能否稳定使用；一排绿色 IP 标签，也不能回答某个账号能否长期正常使用。

读 VPS 测评，最重要的是知道每项证据能回答什么问题。先保留测试条件，再谈适不适合自己。拓扑选择可结合[线路与落地搭配](/vps/relay-and-egress-guide/)阅读。

## 先看测速的方向和阶段

Ping、TCP 建连、TLS、首字节和持续传输反映不同阶段。低 Ping 不保证下载快，TCP 建连很快也不保证后面的 TLS 与业务响应快。

单连接适合观察单流能力，多连接适合观察聚合吞吐。真实应用可能使用两者，不能只选对商家更好看的数字。TCP 与 UDP、IPv4 与 IPv6、闲时与晚高峰也要分开。

iperf3 默认由客户端发送，`-R` 改成服务端发送。记录至少应包括协议、并发数、时长、方向及发送和接收结果。重传的绝对计数不是重传率，要结合传输量和时间判断。[iperf3 官方说明](https://software.es.net/iperf/invoking.html)

curl 的解析、连接、TLS 和首字节时间是从请求开始累计的，不能直接相加；看阶段差值时还要考虑代理协商、复用和重定向。[curl 时间定义](https://curl.se/docs/manpage.html#-w)

## 观察成立，根因也可能仍不确定

晚高峰变慢可能来自拥塞、丢包、路由变化、资源竞争或限速，不能仅凭降速认定 QoS。TCP、UDP 表现不同，也不足以直接证明商家针对大小包做了欺骗性处理。

一个 [DMIT 与 Zouter 互联案例](https://www.nodeseek.com/post-902010-1)报告了双向速度不对称，换另一条路径后明显改善。这支持“应分别测两机双向互联”，但其中“进入 Cloudflare 清洗池”仍是作者的根因推测。

该案例里的 46.9Mbps，换算约为 5.86MB/s，尚未扣除开销。它与报告的下载量级相近，但不能严格解释整个 5～8MB/s 区间。

另一个[台湾 HiNet 案例](https://www.nodeseek.com/post-903287-1)报告了异常低的连接延迟及更长的 TLS 耗时。这提示测量路径可能被前置处理，但不足以确定具体 Split-TCP 实现。正文也没有给出完整包长测试命令，不能直接将“1400 字节通、1401 字节不通”确认为 PMTU 恰好等于 1400。

小请求正常、大传输卡住时，可以检查路径 MTU；不要先照抄固定值。Ping 载荷长度不等于完整 IP 包长，TCP MSS 调整也不是所有 UDP 包长问题的解法。[tracepath 说明](https://man7.org/linux/man-pages/man8/tracepath.8.html)

## 把 IP 的几个维度拆开

ASN、用途分类、真实接入方式、注册归属、数据库定位、网站地区判断和共享人数，分别描述不同事情。

- **ISP 标签**：数据库的用途分类，不能单独证明机器接在住宅宽带上。
- **双 ISP**：圈内对数据库字段的说法，不是两条运营商宽带，也不是住宅真实性认证。
- **原生 IP**：常见营销与圈内分类，不能保证物理位置、路由或目标服务表现。
- **纯净分数**：某套检测体系的结果，不是目标网站的完整风控模型。
- **解锁 Yes**：脚本在当时探测到的可用性，不代表真实账号和所有功能长期可用。
- **送中**：应具体写明哪个服务把出口识别成中国地区，不扩展成所有网站的统一结论。

IP2Location 的 ISP 是用途分类；MaxMind 也明确提供定位准确度范围。数据库意见不同时，没有理由让某一库一票决定真伪。[IP2Location 分类](https://blog.ip2location.com/knowledge-base/what-is-usage-type/)、[MaxMind 准确度](https://support.maxmind.com/knowledge-base/articles/maxmind-geolocation-accuracy)

因此，先核对目标用途的实际体验，再决定是否为住宅属性付费。动态换 IP 可能暂时改变可用性，也可能打断连接，不会清除账号层面的限制。

## 带宽规格和流量账本分开算

“G 口”“10G 口”描述端口或套餐速率，不自动意味着独享、单连接跑满或持续保证。不限流量也可能带公平使用、带宽和用途限制。

计费至少要确认统计方向、接口范围、时间周期和超额处理：单向是只计出站、只计入站，还是另一种口径？内网是否免费？暂停或实例到期后流量池怎么处理？这些都不能凭名称推导。

### 内网免计费减少的是某段计量

```text
用户 ⇄ 优化线路机 ⇄ 免计费内网 ⇄ 普通出口机 ⇄ 网站
```

理想化地说，如果 100GB 业务数据在单台转发机经过公网入和公网出，两边都计费，可能累计约 200GB；其中一侧换成免计费内网，优化机可能只计约 100GB。这里忽略协议开销和反向流量。

这不是带宽翻倍，也不是获得免费额度。另一台机器的公网流量、续费和内网限速仍要计算。GreenCloud、VMRack 的[测评实例](https://meowvps.com/blog/greencloudjp/)与[用户反馈](https://www.nodeseek.com/post-900050-1)可以帮助理解结构，不能作为所有套餐的当前承诺。

### 流量池共享的是额度

流量池让指定实例共用额度，与内网免计费不是一回事，也不合并带宽。它适合本来就需要多个地区、但使用量分布不均的情况。只为了凑额度买闲置机器，未必比直接买合适套餐便宜。

## 低价还要计入恢复和交易成本

首期优惠与循环优惠不同；退款到账户余额也不同于原路退款。历史帖子里的价格、冷却期、赠送权益和手续费，都应在交易时核对。

二手交易中的原邮、改邮和 PUSH 也要区分：前者涉及初始邮箱，改邮涉及账号绑定，PUSH 通常是商家支持的实例过户。PUSH 可以减少接手旧账号的风险，但不消除付款争议和商家规则；持有原邮也不能保证永不被找回。

大盘机的容量与 RAID 同样不是备份保证。同步可能传播误删，备份要能恢复所需历史与一致的数据。运行中的 Vaultwarden SQLite 数据库，应按官方建议使用在线备份等适当方法，而不是只复制主数据库文件。[官方备份要求](https://github.com/dani-garcia/vaultwarden/wiki/Backing-up-your-vault)

## 用证据替代神机标签

一份值得参考的测评，应说明具体套餐、时间、运营商、协议、方向和方法；一套值得采用的方案，应说明收益、额外成本和故障后的行为。

同一作者在论坛与博客转贴，不算两份独立验证。AI 整理稿中的解释也要回到原始数据。把“实测现象”“作者推测”“商家承诺”分开，才能判断一台机器是适合自己的工具，还是只在截图里好看。
